# NotepadXX Parity Matrix — Macro, Run, Plugins, Window, Status Bar, Toolbar, CLI Args

Sources: [npp-user-manual.org](https://npp-user-manual.org/) (Macros, Run Menu, Plugins, Command Prompt, User Interface, Views, Plugin Communication pages) and the Notepad++ GitHub source (`notepad-plus-plus/notepad-plus-plus`, `master` branch): `PowerEditor/src/menuCmdID.h` and `PowerEditor/src/MISC/PluginsManager/Notepad_plus_msgs.h`, fetched directly (raw.githubusercontent.com) on 2026-08-18.

**Legend**
- **Complexity**: S = trivial (hours), M = moderate (days), L = substantial (1-3 weeks), XL = major subsystem (month+)
- **Tier**: E = Essential (v1 blocker, core parity), I = Important (v1-adjacent, high user-visible value), N = Nice-to-have (long tail / low-usage / Windows-specific cruft)

## 1. Macro Menu

Native Notepad++ macros are **pure keystroke/command replay** recorded from the Windows message stream — there is no scripting language, no variables, no conditionals, and no loops other than "repeat N times" or "repeat to EOF". This is a deliberate simplicity/power tradeoff; power users use the NppExec/PythonScript/LuaScript plugins instead. `menuCmdID.h` confirms the macro commands share the `IDM_EDIT` ID block (`IDM_MACRO_STARTRECORDINGMACRO = IDM_EDIT+18`, `..._STOPRECORDINGMACRO = IDM_EDIT+19`, `..._PLAYBACKRECORDEDMACRO = IDM_EDIT+21`, `..._SAVECURRENTMACRO = IDM_EDIT+25`, `..._RUNMULTIMACRODLG = IDM_EDIT+32`), i.e. macros are literally edit-command replay, not a separate execution engine.

| ID | Area | Command/Feature | Default shortcut | Behavior | macOS equivalent/notes | Complexity | Tier |
|---|---|---|---|---|---|---|---|
| MAC-01 | Macro | Start Recording | Ctrl+Shift+R (toggle, doubles as Stop) | Begins capturing every subsequent editor command (keystrokes routed through Scintilla + N++ command IDs, not raw key events) into an in-memory buffer. Toolbar button and menu item both exist; recording indicator changes toolbar icon state. | Record via a **command-log**, not `NSEvent` taps — intercept at our own "action dispatch" layer (the same layer that would back Undo) so replay is deterministic and independent of keyboard layout/IME. Avoid CGEventTap-based literal key recording; it breaks with menu-invoked or trackpad-invoked actions and would fail App Store review. | M | E |
| MAC-02 | Macro | Stop Recording | Ctrl+Shift+R (toggle, same key as Start) | Ends capture. "If you haven't performed any actions during the recording, this buffer will be cleared" — empty macros are discarded silently. | Mirror this: discard zero-length recordings; do not prompt. | S | E |
| MAC-03 | Macro | Playback | None by default (Shortcut Mapper only) | Replays the current in-memory (unsaved) macro buffer once at the caret's current position. Only one "current" macro buffer exists at a time — recording a new one overwrites it unless saved first. | Straightforward once MAC-01's command-log exists: replay the array of recorded actions against current document state. | S | E |
| MAC-04 | Macro | Run a Macro Multiple Times… (dialog) | None by default | Opens a modal with two mutually exclusive modes: (a) **Run N times** — numeric spinner, executes the macro exactly N times in sequence; (b) **Run until end of file** — "perform the macro until the caret reaches the end of the current file (starting from its current position)", i.e. loop until an end-of-buffer/EOF condition halts it (also stops if the macro itself fails to advance, to avoid infinite loops). Works on the saved-or-current macro. | Same two-mode dialog. | MAC-05 | Macro | Save Current Recorded Macro… | None by default | Names the current macro buffer and lets the user assign a default key combination at save time. | MAC-06 | Macro | Modify Shortcut / Delete Macro… | None by default | Opens the Shortcut Mapper's "Macros" tab: rebind or clear a macro's shortcut, or delete the macro entirely. A step editor is a legitimate v2 differentiator since our command-log format is easier to render than raw XML. | M | I |
| MAC-07 | Macro | Saved-macro list (dynamic menu entries) | User-assigned, via MAC-06 | Every saved macro appears as a numbered entry beneath the static Macro menu items and is independently invokable/bindable. | MAC-08 | Macro | Macro storage format (`shortcuts.xml`) | — | Macros are serialized as an ordered list of `<Action type= message= wParam= lParam= sParam= />` elements inside `<Macro name=... Ctrl=... Alt=... Shift=... Key=...>` in `shortcuts.xml` — i.e. a flat replay list of raw Win32/Scintilla message sends. No branching, no variables: this *is* the entire macro "language". | Design our own equivalent JSON/plist "action log" schema (ordered list of internal command invocations with their parameters) stored per-user, e.g. `~/Library/Application Support/NotepadXX/shortcuts.json`. Keep it human-diffable so power users can hand-edit like `shortcuts.xml`. | M | I |
| MAC-09 | Macro | Macro engine limitation (no branching/no scripting) | — | By design. Offer our JS/WASM plugin scripting tier (see Plugins §3 architecture recommendation) as the sanctioned "graduate" path instead of inventing macro-language extensions that would break `.xml`-level parity expectations. | — | E |
| MAC-10 | Macro | Toolbar macro buttons | — | Start/Stop Recording, Playback, Run Multiple Times, Save Current Recorded Macro all have dedicated toolbar icons (see §6 Toolbar). | Same five buttons in our toolbar icon set. | S | I |

### 3.2 Plugin API surface (what a plugin can do) — from `Notepad_plus_msgs.h`

The header defines **118 `NPPM_*` host→plugin-callable messages** and **~35 `NPPN_*` notifications** the host pushes to plugins. Grouped by category (representative members, not exhaustive per-message):

### 3.3 macOS plugin architecture — options considered & recommendation

| ID | Area | Command/Feature | Behavior | macOS equivalent/notes | Complexity | Tier |
|---|---|---|---|---|---|---|
| ARCH-01 | Plugins/Arch | Option A — in-process native `dylib`/bundle (direct DLL-model port) | Mirrors Windows exactly: plugin bundle exports the API-16 functions, host `dlopen`s it into the app process, full synchronous access to every API in §3.2 including raw editor-core message passthrough (API-06). | Maximum compatibility and performance; zero IPC overhead so per-keystroke Scintilla-message plugins (syntax checkers, autocomplete providers) work identically to Windows. **Fatal drawback**: any plugin bug/crash takes down the whole app (matches N++'s actual real-world failure mode, which is *not* something to be proud of copying); cannot be distributed via the Mac App Store (arbitrary unsigned/third-party native code loading is disallowed); every plugin needs notarization or the user must bypass Gatekeeper per-plugin. | L | — |
| ARCH-02 | Plugins/Arch | Option B — XPC service per plugin (one process per plugin) | Each plugin ships as an XPC service bundle; host talks to it over a generated Objective-C/Swift protocol. Crash-isolated (a plugin crash doesn't kill the host), can run under a tighter sandbox profile, and is the pattern Apple itself uses for its own inter-process extensibility (Safari extensions, Finder Sync extensions, Xcode Source Editor extensions). | Sandboxable and thus App-Store-plausible. **Drawback**: high-frequency APIs (API-06's raw editor-core message passthrough, API-04's dockable-panel live rendering) get expensive and awkward over IPC — every Scintilla-equivalent call becomes a round trip, and remote view hosting for dockable panels needs `NSViewController`/`NSXPCConnection`-based remote view plumbing that's genuinely hard to get right (see API-04, marked XL specifically because of this). Realistically limits what "full power" plugins can do without redesigning the hottest APIs into batched/async equivalents. | XL | — |
| ARCH-03 | Plugins/Arch | Option C — embedded scripting/JS (or WASM) engine, in-process interpreter, no native code loading | Plugins are JS (via `JavaScriptCore`, already on every Mac for free) or WASM modules (via a lightweight embedded runtime) run inside a `JSContext`/Wasm sandbox inside the host process, calling into a curated bridge API that mirrors §3.2's NPPM_-equivalent surface (document/view/menu/notification APIs) but **not** raw unrestricted editor-core message passthrough. | Fully sandboxable, App-Store-safe (this is literally how Safari App Extensions and many "scripting" plugin systems — e.g. Sublime Text's Python, VS Code's extension host — stay both powerful and safe), fast to author plugins in (no compilation/signing step for users), crash-isolated by construction. **Drawback**: cannot build genuinely novel native `NSView`-based dockable panels or reach arbitrarily deep into the editor core the way API-06/API-04 plugins do on Windows — a meaningful power ceiling below Option A. | L | — |
| ARCH-04 | Plugins/Arch | **Recommendation: tiered hybrid — JS/WASM scripting tier (default, sandboxed, App Store-safe) + optional native XPC "power plugin" tier (notarized, direct-download only, mirrors Xcode/BBEdit precedent)** | Ship two plugin classes: **(1) Script plugins** — JavaScriptCore-hosted, covering the ~80% case (NppExec-alikes, linters, formatters, snippet tools, most of what's on nppPluginList today) via a curated bridge API translating 1:1 from the NPPM_ groupings in §3.2 (API-01/02/03/07/08/09/10/11/13, plus a *batched* subset of API-06/15 sufficient for common cases — e.g. exposing high-level find/replace/styling calls rather than raw message numbers). Distributed through our own catalog (PLG-07), installable with zero Gatekeeper friction, and App-Store-compatible, unlocking Mac App Store distribution for the main app — something N++ itself, as a Win32 app with unrestricted DLL loading, could never have offered on Windows' equivalent (there is no Windows Store parity concern, but it matters for us). **(2) Native power plugins** — real code (Swift/C++) built against a stable ABI resembling API-16, hosted via XPC service (Option B) for the API-04 dockable-panel and deep lexer-registration (API-05) cases that genuinely need it; distributed only via direct download/notarization, exactly like BBEdit's plugin model or how Xcode Source Editor Extensions work — explicitly *not* App-Store-bundleable, and the app must gracefully run without them (App Store build simply omits the native-plugin loader). | This is the deliberate tradeoff: full power parity is preserved (native tier covers API-04/API-06 use cases 1:1), but it's opt-in and clearly separated from the mainstream distribution channel, rather than either (a) silently failing App Store review by copying Option A wholesale, or (b) quietly capping plugin power at Option C's ceiling and calling it "parity" when it isn't. Flag this tradeoff to Jaber explicitly before implementation — it's a genuine product-strategy fork (App Store presence vs. unrestricted native plugin power), not a pure engineering choice. | XL | E |
